# ADR-0007: 장부 거래일은 미래 날짜를 허용하지 않음

## 맥락
- 장부(매입/매출/지출)는 이미 발생한 거래를 사후에 기록하는 도구다. "내일 이만큼 팔 것이다" 같은
  미래 거래를 미리 등록하는 것은 장부의 개념과 맞지 않는다.
- 기존 정책은 `trx_date`에 과거·미래 날짜를 모두 허용했다 (`LedgerService.create/update`에 날짜
  검증이 없었음).
- 프론트(`ledger.vue`)에서 먼저 `AppDatePicker`에 `max`(오늘)를 적용하고 제출 시점에도 검증을
  추가했지만, 이는 UI 단의 제한일 뿐이다. `POST/PUT /api/ledger`를 직접 호출하면(다른 클라이언트,
  스크립트, 버그 등) 이 제한을 우회해 미래 날짜 거래가 그대로 저장될 수 있는 정책 공백이 있었다.

## 결정
- `LedgerService.create()`/`update()`에 `validateTrxDate(LocalDate)`를 추가해 `trxDate`가
  오늘보다 미래면 `ErrorCode.LEDGER_FUTURE_DATE_NOT_ALLOWED`(`L003`)를 던진다.
- 과거 날짜는 계속 허용한다 — 사용자가 입력을 깜빡한 지난 거래를 사후에 등록하는 경우가 정상
  유스케이스이기 때문.
- ADR-0006 컨벤션에 따라 비즈니스 로직 거부이므로 HTTP `200` + `success:false`로 응답한다.

## 고려한 대안
1. **프론트에서만 제한 (기각)** — API를 직접 호출하면 그대로 우회된다. 장부 데이터 정합성을
   보장하지 못한다.
2. **DB CHECK 제약 (`trx_date <= CURRENT_DATE`) (기각)** — DB 레벨에서도 막을 수는 있지만, 이
   프로젝트는 이미 `validateTrxType`처럼 서비스 레이어에서 비즈니스 규칙을 검증하고 `ErrorCode`로
   일관된 메시지를 응답하는 컨벤션을 따르고 있다. DB 제약 위반은 이 컨벤션과 분리된 에러 경로(SQL
   예외)로 빠져 메시지를 통일하기 어렵다.
3. **서비스 레이어 검증 (채택)** — 기존 `validateTrxType`과 동일한 패턴으로 추가할 수 있고,
   `ErrorCode`/`BusinessException` 체계에 자연스럽게 들어맞는다.

## 결과
- (+) API를 직접 호출해도 미래 날짜 등록이 막힌다 — 프론트 제한과 백엔드 정책이 일치한다.
- (+) 기존 `validateTrxType` 패턴을 그대로 재사용해 구현·테스트 비용이 적다.
- (-) 이미 미래 날짜로 저장된 레코드가 있다면 이번 변경으로 소급 정리되지 않는다 — 신규 검증만
  추가되고 별도 데이터 마이그레이션은 하지 않는다.
